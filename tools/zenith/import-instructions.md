# Importing this fork into the Zenith repository

The launcher will live in `gitzetazero/zenith` under `zenith/launcher/` and be released by that repository's workflow.
This file lists what the import job must do. Nothing in the build depends on this fork's repository name: the update feed,
the Market's User-Agent and `package.json` already point to `gitzetazero/zenith`.

## 1. Copy the tree

Copy the fork's tracked files (`git archive HEAD` or `git ls-files`) into `zenith/launcher/`. It stays a self-contained pnpm workspace
(`zenith/launcher/pnpm-workspace.yaml`, `pnpm-lock.yaml`, `package.json`, `patches/`, `packages/`, `xmcl-*`, `tools/`, `tsconfig.json`,
`vitest.config.mts`): run every command from `zenith/launcher/`, never from the repository root.

Do **not** import:

| Path | Why |
|---|---|
| `.git/`, `node_modules/`, `xmcl-electron-app/dist`, `xmcl-electron-app/build/output` | build products |
| `.github/workflows/*` | the inherited XMCL workflows (`build.yml`, `deploy-*.yml`, `sign-release.yml`, `e2e.yml`, ...) need secrets and publish XMCL things. The fork's `zenith-release.yml` is the model for the new job (section 3) but must be rewritten for the new paths. |
| `e2e/`, `reports/`, `mock/`, `deskgap-app/` | XMCL test/packaging fixtures that Zenith Launcher does not use |
| `CODE_OF_CONDUCT.md`, `CONTRIBUTE.md`, `ModrinthPublish.md`, root `README.md` | replace with `zenith/launcher/README.md` (short, see the fork's README) |

Keep: `LICENSE` (XMCL's MIT licence and copyright, legally required; the existing `zenith/launcher-interim/LICENSE.xmcl` is the same text), `docs/ZENITH-LAUNCHER.md`
(what differs from XMCL) and `docs/branding/`.

Merge with the interim launcher already in the repository (`zenith/launcher-interim/`): when the new release replaces it,
delete the interim folder and its job; `NOTICE.txt`, `README-PORTABLE.txt` and `installer.nsi` of the interim build are not used by electron-builder here
(the NSIS installer is generated by `xmcl-electron-app/build/electron-builder.config.ts`).

The brand kit is shared: `zenith/branding/` stays the source of truth. The fork carries copies (`xmcl-electron-app/icons`, `xmcl-keystone-ui/src/assets/logo.webp`,
`docs/branding`). After the import, regenerate them from `zenith/branding` (`icons/zenith-launcher.ico` -> `dark.ico` and `light.ico`; `png/logo-tile-256.png` -> `dark@256x256.png`,
`light@256x256.png` and `logo.webp`; `png/logo-tile-32.png` -> the `@tray.png` files).

## 2. Paths that change

Everything is relative to `zenith/launcher/`; there are no absolute paths and no references to the fork's name. Check with:

```bash
grep -rn "zenith-launcher" --include=*.ts --include=*.yml --include=*.json --include=*.mjs . | grep -v node_modules
```

The only legitimate matches are the app id / data folder name (`zenith-launcher` in `xmcl-runtime/constant.ts`, `%APPDATA%\zenith-launcher`), the `zenith-launcher://` deep link
scheme and the package name. The bridge: the fork downloads it with `tools/zenith/fetch-bridge.mjs` (signature of `SHA256SUMS` from the `nightly` release, then SHA-256). In the
Zenith repository the bridge is built by the same workflow: replace that step by passing the freshly built `zenith-bridge-windows-x64.exe` to
`xmcl-electron-app/build/zenith/` (the electron-builder config picks it up from there as an extra resource, `pluginZenith.ts` reads it from `process.resourcesPath/zenith`).

## 3. Workflow steps (job `launcher` in `.github/workflows/zenith-release.yml` of the Zenith repository)

`windows-latest`, `working-directory: zenith/launcher` for every step, third-party actions pinned by commit SHA, permissions `contents: read`, and `contents: write` only for the publish step.
The fork's `.github/workflows/zenith-release.yml` has the exact steps:

1. checkout (`persist-credentials: false`), `pnpm/action-setup`, `actions/setup-node` (22, `cache: pnpm`, `cache-dependency-path: zenith/launcher/pnpm-lock.yaml`).
2. `python -m pip install --user packaging setuptools` (node-gyp), `pnpm install --frozen-lockfile`.
3. Bridge: build it in the same run (or `node tools/zenith/fetch-bridge.mjs xmcl-electron-app/build/zenith`).
4. `pnpm run check` (typecheck of `xmcl-runtime-api`, `xmcl-runtime`, `xmcl-electron-app`, `xmcl-keystone-ui`).
5. Tests (see section 4).
6. `pnpm run --prefix xmcl-keystone-ui build` then `pnpm run --prefix xmcl-electron-app build:all` (env: `NODE_ENV=production`, `NODE_OPTIONS=--max-old-space-size=8192`, optional repository variables
   `ZENITH_MSA_CLIENT_ID`, `ZENITH_DISCORD_CLIENT_ID`; variables, never secrets).
7. `node tools/zenith/verify-asar.mjs <win-unpacked/resources/app.asar>` (fails on `xmcl.app`, `1363d629`, `XMCL Agent`, `Together`, `signaling`, Application Insights; requires `.minecraftz`).
8. Collect `Zenith-Launcher-Setup-x64.exe` and `Zenith-Launcher-Portable-x64.exe`, write `SHA256SUMS`.
9. Publish with `gh release create <tag> --prerelease=false --latest ...` (a normal release, not a prerelease).

Tag naming: the launcher looks for the newest published release that carries the asset `Zenith-Launcher-Setup-x64.exe` (`xmcl-runtime/zenith/release.ts`), so the tag may be
`v0.73.1-zenith.N` or `launcher-v0.73.1-zenith.N`; both map to the version `0.73.1-zenith.N`. The asar update (`app-<version>-win.asar` under `releases/download/v<version>/`) is not published, so updates are manual (the launcher
links to `https://github.com/gitzetazero/zenith/releases`). Do not mark a launcher release `latest` if the repository's `latest` must stay the game release: use `--latest=false` then.

Windows `workflow_dispatch` input: `tag`. The Zenith repository also publishes the game (`nightly`): keep the two jobs' concurrency groups separate.

## 4. Tests the import must run

```bash
pnpm run check
pnpm vitest run xmcl-runtime/zenith xmcl-runtime/app xmcl-runtime/infra/plugins xmcl-runtime/moddb \
  xmcl-runtime/instance/InstanceService.icon.test.ts xmcl-runtime/settings xmcl-electron-app/build \
  xmcl-keystone-ui/src/telemetry.test.ts xmcl-keystone-ui/src/i18n.integration.test.ts
```

`xmcl-runtime/zenith` holds the Zenith tests: the `.minecraftz` path (`dataFolder.test.ts`), the Zenith-only instance guard (`only.test.ts`), hard-off telemetry
(`telemetry.test.ts`), the Market's registry client with recorded fixtures (`market/*.test.ts`, fixtures in `market/fixtures`: the real registry index and Modrinth responses, trimmed),
Discord presence (`presence.test.ts`), the update feed (`release.test.ts`), the bridge instance (`instance.test.ts`), blocked hosts, config and Microsoft sign-in messages.
Known to fail on a Windows PC without the symlink privilege (not related to Zenith): `readLinkSafe`, `screenshotSafety`, `safety`, `restoreTransaction`, `BackupService`, and the DeskGap workflow tests.

## 5. Things the maintainer provides

- `ZENITH_MSA_CLIENT_ID`: an Azure app registered and approved by Mojang (redirect `http://localhost:25555/auth`). Without it Microsoft sign-in shows a message.
- `ZENITH_DISCORD_CLIENT_ID`: create a Discord application named **Zenith**, upload the logo as a Rich Presence art asset named `zenith-logo`, and set its application id (repository variable at build time, the environment variable, or `zenith-config.json`). Without it the presence is disabled silently.
- Optionally `CURSEFORGE_API_KEY` (not used by the Market today) and `ZENITH_MOD_INDEX` (an https address of a test registry index).
